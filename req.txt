# FocusAI: Build a Real-Time, Multimodal AI Learning Intelligence Platform

## Role

Act as a senior full-stack engineer, AI engineer, computer vision engineer, database architect, and product designer.

Your task is to inspect the existing FocusAI repository and transform it into a fully functional AI-powered classroom platform. Do not merely redesign the dashboard. Implement the frontend, backend, database, real-time communication, AI integration, document processing, student analytics, and teacher workflows.

Use the existing codebase as the starting point. Preserve working features, inspect existing architecture before making changes, and avoid unnecessary rewrites.

The application must work with actual uploaded teaching materials and real classroom interactions. Do not substitute hardcoded dashboards, fabricated student data, simulated gaze measurements, or random AI insights for working functionality.

# 1. Product Vision

FocusAI helps teachers understand what students are struggling with during a live lesson and respond before students fall behind.

The system must answer four questions:

1. What concept is the teacher teaching right now?
2. Which paragraphs, concepts, or sections are students having difficulty understanding?
3. Is the difficulty affecting an individual student or a significant portion of the class?
4. What should the teacher explain again, emphasize, or clarify?

FocusAI should analyze actual teaching materials, optional consent-based eye-tracking signals, student comprehension tests, direct feedback, and classroom interaction data.

The platform has two roles:

- **Teacher:** Creates classes, uploads materials, conducts live sessions, monitors individual and group learning difficulties, identifies important concepts, and receives AI-generated recommendations.
- **Student:** Joins classes, follows live teaching material, completes short calibration and comprehension tests, provides feedback, and receives personalized learning insights.

The main product feature is a live difficulty-detection and teaching-reiteration system.

# 6. Document Processing and Paragraph-Level Mapping

Teachers must be able to upload:

- PDF documents.
- PPT and PPTX presentations.
- Lecture notes.
- Other document types supported by the implementation.

Build a document-processing pipeline that extracts the actual content.

For each document, preserve:

- Document ID and ownership.
- Page or slide number.
- Paragraph or content-block identifier.
- Text and headings.
- Text position or bounding boxes when available.
- Related images, diagrams, and equations when relevant.
- Processing status and extraction confidence.

Create a stable content map that lets the application identify an exact paragraph, slide, or section.

For PDFs, use text extraction when possible and OCR for scanned documents when needed. For PowerPoint files, preserve individual slide boundaries and extract text from their actual contents.

When the document is rendered in the student interface, maintain a mapping between the displayed text and its stored paragraph identifiers.

This mapping is essential: a gaze estimate is useful only if the application can associate it with a specific displayed text region.

If a paragraph cannot be mapped reliably, mark its tracking status as unavailable rather than assigning a false paragraph-level difficulty score.

Support document processing in the background. Display upload progress, processing status, and meaningful errors.

# 7. Student Calibration and Comprehension Tests

Before using eye-tracking data, implement a short calibration and validation flow.

The purpose is to establish how reliably a student's gaze can be estimated and whether the system can associate it with the correct displayed region.

### Calibration flow

1. Explain the purpose of camera access and request explicit permission.
2. Let the student opt out without losing access to normal classroom features.
3. Guide the student through a small set of calibration targets distributed across the screen.
4. Estimate gaze-to-screen mapping.
5. Evaluate calibration quality using held-out targets or another independent validation procedure.
6. Show the student whether calibration is usable.
7. Allow recalibration if accuracy is insufficient.

Do not claim precise paragraph tracking when the calibration error is too high.

### Comprehension validation

Create short tests that can be associated with actual document sections.

Support:

- Teacher-created questions.
- AI-generated questions grounded in the current slide.
- Multiple-choice comprehension checks.
- Brief explanations or confidence ratings where appropriate.
- Before-and-after comparisons when suitable.

For example, after a student reads a paragraph about Newton's second law, the system may ask a short question about the relationship between force, mass, and acceleration.

Store the actual answer, correctness where determinable, timestamp, associated paragraph or concept, and confidence response if collected.

Use these tests to help validate difficulty predictions. Eye movements alone must never be treated as ground truth.

# 8. Privacy-Conscious Eye Tracking and Facial Analysis

Implement optional, consent-based webcam analytics.

Important distinction: this is facial landmark and gaze analysis, not facial identity recognition.

Use Supabase authentication to establish who the student is. Do not identify students by matching their faces, create face-recognition profiles, or infer their identity from biometric features.

### Signals to estimate

When the student opts in and the camera is functioning, estimate:

- Gaze position on the screen.
- Whether the gaze intersects a mapped paragraph region.
- Approximate dwell time within a paragraph.
- Number and duration of returns to a paragraph.
- Reading progression through the displayed text.
- Confidence and quality of the gaze estimate.
- Periods when the estimate is unavailable or unreliable.

Do not treat frequent rereading, long dwell time, or looking away as definitive evidence of confusion.

A student may reread because they are interested, thoughtful, distracted, or already understand the material.

### Privacy requirements

- Obtain explicit, informed camera consent.
- Provide a clear opt-out and camera-off state.
- Prefer on-device video processing.
- Do not upload or persist raw webcam footage by default.
- Avoid storing face images, face embeddings, or identity templates.
- Send only the minimum derived signals necessary for the product.
- Clearly explain that gaze estimates are approximate.
- Provide a way to disable camera analytics independently of classroom participation.
- Apply age-appropriate privacy protections if minors use the platform.

The system must remain useful without webcam access through comprehension tests, student feedback, and interaction analytics.

# 9. Multimodal Difficulty Estimation

Build a difficulty-estimation service that combines independent evidence sources.

Possible inputs include:

1. Gaze dwell time and reading progression.
2. Repeated returns to a paragraph.
3. Comprehension question results.
4. Student-reported confusion.
5. Requests for clarification.
6. Confidence ratings.
7. Class-level patterns across the same content.

Create a transparent and configurable scoring approach.

Do not assume that these signals have universally correct weights. Begin with a simple, explainable rule-based baseline, record its outcomes, and evaluate whether the scores predict observed comprehension difficulties before introducing more complex models.

Every paragraph-level estimate must include:

- Content block and slide identifiers.
- The number of students with sufficient observations.
- The number and percentage with evidence of difficulty.
- The evidence sources available.
- Data quality and confidence.
- The time window.
- A status such as `insufficient_data`, `monitoring`, `difficulty_detected`, or `important`.
- The distinction between observed behavior and inferred difficulty.

Do not label an individual student as struggling solely because of gaze behavior. Prefer corroborating evidence from comprehension checks or explicit feedback.

Keep difficulty estimation separate from AI-generated explanations. A model may suggest why a paragraph is confusing, but the underlying evidence and counts must come from actual observations.

# 10. The Two Core Flags: Difficult and Important

Implement two distinct flags throughout the product.

## Flag A: Difficult

The Difficult flag identifies paragraphs or concepts where evidence suggests students are having trouble.

A paragraph may be marked Difficult when a configurable rule is met using available, sufficiently reliable signals.

Show:

- Paragraph or concept.
- Slide number.
- Number of affected students.
- Number of students with valid observations.
- Difficulty percentage.
- Evidence and confidence.
- Suggested teacher action.

The Difficult flag must be updated as new feedback and test results arrive.

Do not generate a Difficult flag merely because a paragraph contains complex vocabulary or because one student looked at it for a long time.

## Flag B: Important

The Important flag identifies concepts that deserve emphasis, even if students are not currently struggling.

Determine importance from grounded evidence such as:

- Teacher-selected learning objectives.
- Explicitly marked important material.
- Key definitions, formulas, and concepts.
- Prerequisites for later topics.
- Relevance to stated learning outcomes.
- Instructor-confirmed emphasis.

Use Gemma to suggest important concepts from actual lesson content, but make the rationale visible and allow the teacher to override the suggestion.

Important and Difficult must remain independent. A paragraph may be:

- Important only.
- Difficult only.
- Both Important and Difficult.
- Neither.

Do not confuse the importance of a concept with the measured difficulty students experience.

# 11. Group Difficulty Threshold and Automatic Reiteration

Implement the main class-level trigger.

The teacher must be able to configure:

- Number of enrolled or expected students.
- Minimum number of valid observations.
- Difficulty threshold.
- Whether the trigger uses a count, percentage, or both.
- Whether reiteration requires teacher approval or starts automatically.
- Which feedback signals count as difficulty evidence.

### Default example

For a class of 40 students, configure the difficulty threshold as 10 students.

Interpret the threshold precisely:

**Trigger when more than 10 eligible students show evidence of difficulty on the same content section.**

That means:

- 8 affected students: no threshold alert.
- 10 affected students: no threshold alert.
- 11 affected students: threshold reached.

These are example counts, not fabricated live metrics.

Only count eligible students once per paragraph and evaluation window. Prevent repeated events from inflating the count.

Track both the affected count and the denominator. For example, 11 affected students out of 40 expected students is 27.5%, but 11 affected students out of only 20 valid observations is 55% of observed students.

The teacher dashboard must display the distinction clearly.

If insufficient students have valid observations, show an insufficient-data state instead of claiming that the whole class understands or struggles with the topic.

### Live reiteration workflow

When the configured trigger is reached:

1. Identify the specific paragraph, concept, slide, and evidence that triggered the alert.
2. Persist the threshold event.
3. Notify the teacher dashboard in real time.
4. Show the affected count, denominator, percentage, and signal quality.
5. Ask Gemma to generate a short, context-grounded alternative explanation using the actual material.
6. Include a simple example, analogy, or comprehension question where appropriate.
7. Let the teacher review, edit, approve, or dismiss the suggestion.
8. When approved, broadcast the reiteration to the class.
9. Allow the teacher to resume the original lesson.
10. Offer a short follow-up comprehension check.
11. Compare the follow-up results with the earlier results.

Support an explicitly configured automatic mode, but keep teacher approval as the default.

Never allow the AI to unexpectedly interrupt a class because of one noisy signal or a duplicated event.

Add a cooldown and a unique threshold-event identifier so that the same issue does not generate repeated alerts on every update.

After reiteration, record the intervention and subsequent evidence. Do not declare the issue resolved until sufficient follow-up evidence exists.

# 12. Gemma 4 Through Ollama

Use the local Gemma 4 installation as the primary AI inference engine.

Create a dedicated AI service rather than calling Ollama independently from frontend components.

The frontend must never connect directly to Ollama or expose its endpoint to untrusted clients.

Configure the backend using environment variables such as:

- `OLLAMA_BASE_URL`
- `OLLAMA_MODEL`

Use the installed model tag after verifying it with Ollama. Do not hardcode an unverified tag.

The AI service should support the following tasks.

### Material analysis

- Summarize the current slide.
- Extract important concepts.
- Identify potentially confusing terminology or reasoning steps.
- Generate questions grounded in the actual material.
- Explain concepts at different levels of complexity.

### Difficulty explanation

Given an actual paragraph, associated student feedback, and valid aggregate signals, suggest plausible sources of confusion.

Distinguish observed evidence from hypotheses. Do not infer the thoughts or mental state of an individual student from their face.

### Live reiteration

Generate a short alternative explanation that:

- Refers to the actual paragraph or concept.
- Preserves factual correctness.
- Uses an appropriate example or analogy.
- Avoids introducing unsupported facts.
- Includes a short comprehension question.
- Can be reviewed by the teacher.

### Important concept extraction

Identify candidate definitions, formulas, prerequisite concepts, and learning objectives. Store the rationale and allow teacher confirmation.

### Structured output

Where supported by the selected model, use schema-constrained structured output and validate every response.

Otherwise, request a structured format and validate it before use.

Implement:

- Connection and model availability checks.
- Request timeouts.
- Error handling.
- Cancellation for obsolete slide analyses.
- Bounded context windows.
- Debouncing and request deduplication.
- Caching where appropriate.
- Model response validation.
- Clear loading and failure states.

When the teacher advances to a new slide, discard or mark obsolete any pending analysis for the previous slide so it cannot overwrite current insights.

Keep non-AI classroom functionality operational when Ollama is unavailable.

Do not use random fallback responses or hardcoded subject-specific outputs when inference fails.

# 13. Real-Time Architecture

Use a server-authoritative event-driven architecture.

Suggested event types:

- `CLASS_CREATED`
- `SESSION_STARTED`
- `SESSION_PAUSED`
- `SESSION_RESUMED`
- `SESSION_ENDED`
- `MATERIAL_UPLOADED`
- `MATERIAL_PROCESSED`
- `SLIDE_CHANGED`
- `CALIBRATION_COMPLETED`
- `GAZE_SIGNAL_UPDATED`
- `COMPREHENSION_RESPONSE_SUBMITTED`
- `STUDENT_FEEDBACK_SUBMITTED`
- `DIFFICULTY_SCORE_UPDATED`
- `DIFFICULTY_THRESHOLD_REACHED`
- `IMPORTANT_FLAG_UPDATED`
- `REITERATION_PROPOSED`
- `REITERATION_APPROVED`
- `FOLLOWUP_TEST_COMPLETED`

Define typed event payloads with validation and authorization.

Use Supabase Realtime for database changes and presence where appropriate. Do not broadcast every webcam frame or raw gaze sample through database change subscriptions.

Batch derived gaze signals locally and send only appropriate aggregated observations. Keep high-frequency sensor processing separate from the reliable session-state channel.

For each event:

1. Validate the user, role, class, and session.
2. Validate and deduplicate the event.
3. Update authoritative state.
4. Persist relevant observations or state transitions.
5. Recompute affected aggregates.
6. Evaluate threshold conditions.
7. Invoke Gemma asynchronously when needed.
8. Broadcast authorized updates.

Make operations idempotent. Ensure events from one class or session cannot affect another.
